# УНИВЕРСАЛЬНЫЙ СТАНДАРТ РАЗРАБОТКИ FRONTEND (React + TypeScript)

## 1. Категорические запреты (Hard Invariants)

- **Запрещен тип `any` и неявные приведения типов:** Строгая типизация во всем проекте (`strict: true`). Любые структуры данных, ответы бэкенда, параметры запросов и состояния объявляются через интерфейсы или типы (`type`, `interface`). Для неизвестных данных извне используется `unknown` с последующей проверкой (type guards или валидацией через Zod).
- **Запрещены заглушки и мертвый код:** Никаких `// TODO: implement later`, пустых обработчиков `onClick={() => {}}` или фейковых таймеров-заглушек. Каждый элемент интерфейса обязан либо выполнять реальное действие (мутация, навигация, открытие диалога), либо быть заблокирован (`disabled`) с поясняющим тултипом. Если запрос требует заглушек - реализуй их с помощью интерфейсов и принципа инверсии зависимостей.
- **Запрещены каскадные войны стилей и смешивание подходов:** В проекте выбирается **одна** парадигма стилизации (например, *Tailwind CSS* **или** *дизайн-токены компонентной библиотеки типа Ant Design/MUI*). Категорически запрещено создавать разрозненные `.css` или `.module.css` файлы под каждый чих с переопределениями через `!important`.
- **Запрещена ручная перезагрузка страницы (`window.location.reload()` / F5):** Все переходы, мутации данных, смена сущностей и сбросы форм происходят бесшовно и реактивно.
- **Запрещено прямое дублирование серверного состояния в локальный стейт:** Данные, пришедшие с API, не копируются в `useState` компонента без явной необходимости (например, черновик редактирования). Источником правды для серверных данных является только кэш библиотеки запросов (TanStack Query).
- **Запрещено хранение секретов и критических токенов в незащищенных местах:** `localStorage` не используется для сессионных токенов, если планируется встраивание в `iframe` или мобильные WebViews (используется память приложения / `sessionStorage` / `httpOnly cookies`).
- **Запрещены бессмысленные и очевидные комментарии в коде. Комментарий пишется только если фрагмент кода представляет редкое решение  или сложный алгоритм**

## 2. Базовый стек и распределение ответственности

| Слой / Задача | Инструмент | Зона ответственности |
| :--- | :--- | :--- |
| **UI-библиотека** | React (v19+) | Декларативный рендеринг компонентов |
| **Типизация** | TypeScript (v5+) | Контракты данных, безопасность типов на этапе компиляции |
| **Серверный стейт** | TanStack Query (v5) | Кэширование, дедупликация запросов, фоновая синхронизация, optimistic updates |
| **Клиентский стейт** | Zustand | Исключительно глобальный UI-стейт (тема, сайдбары, фильтры, токен активной сессии) |
| **Сетевой транспорт** | Axios | Единый инстанс, перехватчики авторизации (Bearer), единый парсинг ошибок |
| **Маршрутизация** | React Router (v7+) | Клиентский роутинг, вложенные маршруты (Layouts), Guards (защита роутов) |
| **Работа со временем** | Day.js | Легковесная работа с датами, таймзонами и таймерами |

## 3. Архитектура кодовой базы (Feature-Sliced Lite)

Структура строится на принципе слабого зацепления и высокой связности (Low Coupling, High Cohesion):

```text
src/
├── api/                       # Сетевой слой приложения
│   ├── client.ts              # Инстанс Axios, интерцепторы токенов и ошибок
│   └── queryKeys.ts           # Фабрика ключей кэша TanStack Query
│
├── types/                     # Единый источник правды по типам данных (Contracts)
│   ├── api.ts                 # Обертки ответов (ApiResponse<T>, ApiError, Pagination)
│   ├── auth.ts                # Пользователи, роли, сессии, токены
│   └── [domain].ts            # Доменные сущности (зеркало DTO бэкенда)
│
├── theme/                     # Централизованная дизайн-система
│   └── tokens.ts              # Палитра, радиусы, шрифты, отступы, темы
│
├── store/                     # Глобальное состояние приложения (Zustand)
│   ├── useAuthStore.ts        # Токен, базовый профиль, права доступа
│   └── useUiStore.ts          # Модалки, сайдбар, фильтры экранов
│
├── hooks/                     # Общие инфраструктурные хуки
│   ├── useDebounce.ts         # Дебаунс ввода для поиска
│   └── useBreakpoint.ts       # Определение типа устройства (mobile/desktop)
│
├── components/                # Переиспользуемые атомарные UI-компоненты
│   ├── layout/                # Каркас: Header, Sidebar, Footer, ResponsiveContainer
│   ├── feedback/              # EmptyState, ErrorBoundary, LoadingSpinner
│   └── ui/                    # Атомарные элементы (кнопки, бейджи, карточки)
│
├── features/                  # Бизнес-модули (Срезы функционала)
│   └── [feature-name]/        # Пример: user-profile, catalog-feed, item-editor
│       ├── api/               # Специфичные запросы и мутации модуля (useItemQuery...)
│       ├── components/        # Внутренние компоненты конкретно этой фичи
│       └── index.ts           # Публичный API модуля
│
├── pages/                     # Страницы приложения (композиция Layout + Features)
│   └── [PageName].tsx
│
├── utils/                     # Чистые вспомогательные функции (форматтеры, парсеры)
├── App.tsx                    # Провайдеры (QueryClient, Theme, Router)
└── main.tsx                   # Точка монтирования в DOM
```

### Правила импортов между слоями:
1. `pages` могут импортировать из `features`, `components`, `store`, `hooks`.
2. `features` **не могут** импортировать код из соседних `features` напрямую (только через публичный интерфейс `index.ts` или вынос общей логики в `components`/`hooks`).
3. `components` не знают о бизнес-логике конкретных `features` (они принимают данные строго через `props`).

## 4. Паттерны проектирования компонентов

### 4.1. Закон трех состояний данных
Любой компонент или экран, отображающий асинхронные данные, **обязан явно обрабатывать 3 сценария**:
1. **Загрузка (Loading):** Скелетоны (`Skeleton`) или аккуратные спиннеры. Интерфейс не должен дергаться при загрузке.
2. **Пустое состояние (Empty State):** Если массив пуст (`items.length === 0`), отображается специализированный компонент (иконка, понятный текст, почему пусто, и кнопка действия: «Сбросить фильтры» или «Создать первую запись»).
3. **Ошибка (Error State):** Понятное сообщение с возможностью повторить запрос (`retry`).

### 4.2. Изоляция бизнес-логики через кастомные хуки
Компоненты представления (View) не должны содержать громоздкие цепочки преобразования данных:
* Запросы и мутации выносятся в кастомные хуки в папку `features/[name]/api/`:
  ```typescript
  // Правильно: компонент вызывает понятный хук
  export const UserList = () => {
    const { users, isLoading, deleteUser } = useUsers();
    if (isLoading) return <UsersSkeleton />;
    return <UsersTable data={users} onDelete={deleteUser} />;
  };
  ```

### 4.3. Атомарность файлов
* Если размер файла компонента превышает **150–200 строк**, он декомпозируется: выносятся подкомпоненты (строка таблицы, карточка, тулбар) в локальную папку `components/` внутри данной фичи.
* Типы пропсов объявляются явно в начале файла компонента: `interface ComponentNameProps { ... }`.

## 5. Сетевой слой и управление кэшем (TanStack Query)

### 5.1. Фабрика ключей запросов (`queryKeys.ts`)
Ключи запросов никогда не пишутся строковыми литералами в компонентах. Они централизованы:
```typescript
export const queryKeys = {
  users: {
    all: ['users'] as const,
    list: (filters: UserFilters) => [...queryKeys.users.all, 'list', filters] as const,
    detail: (id: string) => [...queryKeys.users.all, 'detail', id] as const,
  },
  items: {
    all: ['items'] as const,
    detail: (id: string) => [...queryKeys.items.all, id] as const,
  }
};
```

### 5.2. Паттерн мутаций и инвалидации
Каждая мутация обязана инвалидировать затронутые запросы:
```typescript
export const useUpdateItem = () => {
  const queryClient = useQueryClient();
  
  return useMutation({
    mutationFn: (payload: UpdateItemDto) => api.patch(`/items/${payload.id}`, payload),
    onSuccess: (data, variables) => {
      // Инвалидируем и точечный элемент, и общий список
      queryClient.invalidateQueries({ queryKey: queryKeys.items.detail(variables.id) });
      queryClient.invalidateQueries({ queryKey: queryKeys.items.all });
      showNotification.success('Изменения успешно сохранены');
    },
    onError: (error) => {
      // Ошибки глобально перехватываются интерцептором, 
      // но локально можно сбросить специфичное состояние формы
    }
  });
};
```

## 6. Сетевой клиент и обработка ошибок (`src/api/client.ts`)

1. **Request Interceptor:**
   * Проверяет наличие токена в `useAuthStore`.
   * При наличии инжектирует заголовок `Authorization: Bearer <token>`.
2. **Response Interceptor:**
   * **401 Unauthorized:** Очищает токен, перенаправляет на экран логина или запускает процедуру silent refresh.
   * **403 Forbidden:** Показывает уведомление о нехватке прав.
   * **422 Validation Error / 400 Bad Request:** Извлекает структурированное сообщение валидации от бэкенда (`error.response?.data?.detail` или `message`) и показывает пользователю в уведомлении.
   * **5xx Server Error:** Показывает стандартизированное сообщение: *«Сервис временно недоступен. Попробуйте позже»*.

## 7. Протокол проверки качества и сборки (CI/CD Gates)

Перед тем как задача считается выполненной, проект обязан пройти **3 последовательных этапа проверки**. Агент или разработчик запускает их строго по очереди:

### Шаг 1. Быстрая проверка типов (Fast Typecheck)
Запускается легковесная проверка без генерации бандла:
```bash
npx tsc --noEmit
```
*Команда обязана завершиться с кодом 0. Никаких ошибок типов, отсутствующих пропсов или несовместимых интерфейсов.*

### Шаг 2. Статический анализ и линтинг (Linter)
```bash
npx eslint src/ --fix
```
*Устраняет неиспользуемые переменные, ошибки хуков (`react-hooks/exhaustive-deps`) и форматирование.*

### Шаг 3. Финальная проверка продакшен-сборки (Production Build)
Запускается **только после** успешного прохождения первых двух шагов:
```bash
npm run build
```
*Проверяет корректность сборки бандлера (Vite/Rspack), оптимизацию импортов и создание артефактов в `dist/`.*  
**Текущее окружение - Windows, терминал cmd.**

## 8. Определение готовности задачи (Definition of Done)

Задача считается выполненной, если:
1. `npx tsc --noEmit` и `npm run build` отрабатывают без единой ошибки.
2. Реализованы все состояния интерфейса: загрузка, пустой экран, показ ошибок.
3. Добавлены понятные типы для всех новых структур данных в `src/types/`.
4. В кодовой базе нет хардкода API-ключей, тестовых паролей или моковых данных внутри продакшен-компонентов.
