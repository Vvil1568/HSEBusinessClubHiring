# Бизнес-клуб · Платформа стартапов и вакансий

Прототип модуля нетворкинга и поиска команды для Telegram Mini App Бизнес-клуба ВШЭ с веб-интерфейсом для ПК и мобильных устройств.

* **Демо:** [t.me/hse_club_hiring_vvi_bot/hiring](https://t.me/hse_club_hiring_vvi_bot/hiring) *(или прямая ссылка на развернутый веб)*
* **Стек:** Python 3.12 (FastAPI, SQLAlchemy 2.0, Pydantic v2, uv), PostgreSQL 16, React 19 (TypeScript, Ant Design 5, TanStack Query v5), Dufs, Docker Compose.

---

## ⚡ Быстрый запуск

Для запуска всего контура (PostgreSQL + Хранилище Dufs + Бэкенд + Фронтенд) требуется только установленный Docker:

```bash
docker compose up --build
```

После старта:
* **Интерфейс приложения:** `http://localhost:5173`
* **Swagger API документация:** `http://localhost:8000/docs`
* **Healthcheck бэкенда:** `http://localhost:8000/health`

Миграции базы данных накатываются автоматически при старте контейнера бэкенда, системные шаблоны вакансий и тестовые данные сидируются в базу данных на этапе старта.  

Для промышленного запуска используйте docker-compose.prod.yml:

```bash
docker compose -f docker-compose.prod.yml up --build
```

Для проверки фронтенда в открыве от бекенда можно запустить mock-версию фронтенда:

```bash
docker compose -f docker-compose.mockfront.yml up --build
```

## 🧪 Тестовые аккаунты и проверка сценариев

В приложении реализован сквозной сценарий: **создание проекта и вакансий $\to$ поиск и отклик другим участником $\to$ модерация отклика автором**.

Для удобства проверки без необходимости перелогиниваться через разные Telegram-аккаунты в интерфейс встроен **плавающий DEV-переключатель личностей** (круглая кнопка в правом нижнем углу):

1. **Иван (Основатель, `founder`)** — владеет стартапом *NeuroPilot AI*, имеет активные вакансии и входящие отклики.
2. **Анна (Соискатель, `applicant`)** — откликается на вакансии, просматривает статусы своих заявок в личном кабинете.
3. **Павел (Новый пользователь, `empty`)** — чистый профиль без стартапов и откликов (для проверки пустых состояний / Empty States).
4. **Текущий пользователь (`real`)** — активирует чтение настоящей подписи Telegram `initData` (доступно при открытии внутри мессенджера).

### Проверка базового флоу за 1 минуту:
1. Зайдите в приложение (по умолчанию активен **Иван**). Перейдите в `/startup/new` и опубликуйте стартап с вакансией.
2. Откройте плавающий переключатель снизу справа и выберите **Анну**.
3. Перейдите в ленту «Вакансии», найдите созданную позицию и отправьте отклик с мотивационным письмом и PDF-файлом.
4. Переключитесь обратно на **Ивана**, откройте статистику своей вакансии (`/vacancy/:id/stats`) и нажмите **«Принять»** на карточке Анны.
5. Переключитесь на **Анну** и откройте раздел «Мои отклики» в профиле — статус заявки сменился на *«Подтверждено»*.

## 🛠 Ключевые архитектурные решения и допущения

### 1. Ролевая модель: ReBAC вместо жесткого RBAC
В системе намеренно нет глобальных ролей `ROLE_FOUNDER` или `ROLE_CANDIDATE`. В реальном сообществе один и тот же человек может быть фаундером в одном проекте и соискателем в другом. Права вычисляются на основе владения объектом (Resource-Based Access Control):
* Редактировать проект, закрывать вакансии и модерировать отклики может только создатель (`startup.owner_id == user.id`).
* Откликаться может любой пользователь, кроме самого создателя стартапа (попытка откликнуться на свою вакансию пресекается на уровне API кодом `422`).
* Повторный отклик на ту же вакансию блокируется на уровне уникального композитного индекса БД и отдает `409 Conflict`.

### 2. Аутентификация в Telegram Mini App и решение проблемы `<img src>`
* Авторизация внутри Telegram происходит без форм логина: бэкенд проверяет криптографическую подпись `initData` через `HMAC-SHA256` с токеном бота и валидирует свежесть `auth_date` (до 24 часов).
* **Защита от Replay-атак:** хэш входящей строки фиксируется в таблице `telegram_auth_nonces`. Повторная отправка той же строки отклоняется (`401 Unauthorized`).
* **Проблема загрузки картинок:** Браузер не может передать кастомный заголовок `X-Telegram-Init-Data` внутри обычного тега `<img src="...">`. Поэтому после валидации Telegram-сессии бэкенд выставляет сессионный HttpOnly-cookie `hb_session`. Запросы из JS идут по заголовку, а теги картинок авторизуются через cookie.
* **Изоляция DEV-режима:** Эндпоинты ручного переключения пользователей (`/auth/dev-login`) защищены проверкой `settings.dev_mode_enabled`. Если бэкенд запущен с `APP_ENV=production`, эти маршруты принудительно возвращают `404 Not Found`, а синтетические токены отбрасываются валидатором HMAC.

### 3. Безопасность файлов и изоляция хранилища (Dufs)
* Файловый сервер Dufs закрыт во внутренней сети Docker и не опубликован наружу. Прямой доступ к нему с фронтенда запрещен.
* Все операции идут через эндпоинты `/api/v1/files/*`:
  * Валидация размера: логотипы до 2 МБ, вложения до 10 МБ.
  * Белый список MIME-типов для картинок (PNG, JPG, WEBP, GIF, SVG).
  * Имена файлов на диске заменяются на `UUID` для защиты от Path Traversal.
  * **Приватность резюме:** вложение к отклику могут прочитать только два человека — сам кандидат и автор вакансии, на которую подан отклик. Для остальных эндпоинт отдает `403 Forbidden`.

### 4. Идемпотентность просмотров и статистика
Просмотры вакансий фиксируются в таблице `vacancy_views` с составным первичным ключом `(vacancy_id, user_id, view_date)`. Вызов `POST /vacancies/{id}/view` идемпотентен: повторные заходы пользователя на страницу в течение одних суток не накручивают счетчик. Просмотры от самого владельца вакансии игнорируются.

### 5. Адаптивность (Mobile-first + Desktop)
Интерфейс спроектирован под двойную модель использования:
* Внутри мобильного Telegram: одноколоночный вид, навигация табами, крупные сенсорные кнопки, адаптивные высоты с учетом экранной клавиатуры (`viewportStableHeight`).
* На десктопе в браузере: двухколоночная сетка (Master-Detail), фильтры в сайдбаре, ховер-эффекты для курсора мыши.
* График динамики просмотров и откликов на экране статистики написан на нативном CSS/HTML Flexbox без подключения тяжелых чарт-библиотек, что снизило размер бандла и устранило артефакты ресайза на узких мобильных экранах.

## Подход к AI-native разработке (написано автором вручную)

Разработка приложения велась по следующей методике.  
Сначала я описываю фронтенд приложения, его экраны, ожидаемое расположение элементов при адаптивности, функционал, собираю цветовую палитру, и прочее.
Затем я беру заготовку системы под FastAPI, React, PostgreSQL. Там у меня лежат настроенные шаблоны проекта, файл ограничения захвата контекста для ИИ-агента (я использую ZooCoder, поэтому у меня это .rooignore), продуманные инструкции с 
правилами качественной разработки на данном стеке. Дорабатываю верхнеуровневую архитектуру системы. В данном случае понадобилось файловое хранилище под логотипы, файлы резюме. Для легковесности я выбрал dufs, так как MinIO здесь явно избыточно.
После этого я запрашиваю генерацию фронтенда с заглушечной реализацей АПИ-слоя. Результат проверяется транспилятором тайпскрипт, линтером. За исполняемыми командами я внимательно слежу. При генерации контролирую архитектурные аспекты и безопасность.  
**Например**, когда нейросеть попыталась реализовать прямой доступ к dufs, для загрузки файлов резюме, я вмешался в ход генерации и предложил вариант с оберткой в виде бекенда, чтобы обеспечить контроль над записью и разграничение доступа
к файлам.  
Когда код сгенерирован и формальные проверки пройдены - проверяю логику фронтенда, визуал, прохожусь по функционалу, произвожу шлифовку. Если логика фронтенда устраивает - двигаюсь в сторону бекенда.
Запрашиваю генерацию ER-диаграммы БД, списка эндпойнтов по категориям. Валидирую и корректирую их. После - генерирую код бекенда, проверяю места, касающиеся безопасности. В конце проверяю приложение в работе, при необходимости
запрашиваю дополнительные исправления по всей базе проекта. Разворачиваю на машине и подключаю к телеграмму.
